## 経緯

このアプリのソースコードはGitHubのどのリポジトリにも存在しなかったため、

## アプリの構成

3ファイルだけの小さなアプリ。

| ファイル | 役割 |
|---|---|
| `server.js` | 198行のExpressサーバー。データ保存・認証・静的配信 |
| `package.json` | 依存はexpressのみ |
| `public/index.html` | アプリ本体（239KB・CSS/JS全部入り） |

### データの置き場所

- **サーバーが正**：`/data/state.json`（Fly.ioの永続ボリューム `vol_r682ye1en6em1gp4`・1GB）
  - `auto_backup_enabled: true` / 5世代保持で日次の自動バックアップあり
  - デプロイしてもデータは消えない
- localStorage は端末側のキャッシュ（オフライン時は後送）
- 見本の写真・動画は `/data/media/`

### 定義は店舗ごと

清掃項目・エリア構成・時間帯リストは店舗ごとに独立していて、
`sdef_<店舗>_<キー>` という名前で保存される。店舗別が無ければ共通キーにフォールバック。

- 時間帯は **朝番(`routine_asa`) / 中番(`routine_hiru`) / 遅番(`routine_ban`)**
- 時間帯リストの項目は画面から追加されたカスタム項目（`customItems_routine_*`）
- 組み込み項目を消す場合は `hiddenItems_<エリア>` にIDを足す方式

### 認証

サーバーの環境変数（Fly secrets）に設定済み。

| 変数 | 用途 |
|---|---|
| `BASIC_PASS` | マスター合言葉（店舗選択あり） |
| `PASS_KASADERA` / `PASS_BIWAJIMA` / `PASS_HAGINO` | 店舗別の合言葉（その店舗に固定される） |
| `ADMIN_PASS` | 「店舗まとめ」表示のゲート |

`/api/*` はクッキー認証。ツールからは Basic認証（パスワード＝`BASIC_PASS`）でも通る。
ページ自体は誰でも開ける（データだけ保護されている）。

クッキーの値は**店舗ごとに違う**（`sha256('gcc-v2:' + BASIC_PASS + ':' + 店舗名)`）。
マスター合言葉は店舗名なしの値。これによりサーバーが「どの店舗の端末か」を判定でき、
`req.authStore` として各APIから参照できる。

> 以前は店舗合言葉でもマスターと同じクッキーを出していたため、店舗の切り分けが
> 画面上の見た目だけだった（`lockedStore` は店舗名を5回タップで解除できる）。
> 在庫システムへ渡す拠点をサーバーで確定させるために分離した。
> 版を `gcc-v1` → `gcc-v2` に上げているので、**反映時に全端末が一度だけ再ログインになる**。

### 担当者名の自動セット

`server.js` が予約システム（`gym-reservation-system` のJobcan取込データ）から
毎日シフトを取得し、`staffRoster` と `shiftSchedule_<店舗>` を自動更新している。
そのため担当者欄はシフト表に基づいて自動で入る。

### 2-3. 朝番・中番・遅番の項目を画面から編集できるようにした

やることリストの上部に「項目を編集」ボタンを置いた。押すと編集モードになり、
各行に「上へ／下へ／編集／削除」が出て、末尾に「＋ 項目を追加」が出る。

- 追加・編集・削除は**他のエリアと同じ既存の仕組み**（`openAddDialog` /
  `openEditDialog` / `deleteItem`）をそのまま使っている。保存先も同じで、
  `defWrite` 経由で `sdef_<店舗>_customItems_<エリア>` に入る（店舗別）
- 並べ替え（`moveRoutineItem`）だけ新規。やることリストは「上から順に」なので
  順番に意味があり、追加した項目は末尾に入るため必要になる。
  入れ替えるのは同じ区分（section）の中の隣どうし
- **切り替え式にした理由**：通常の使用中に編集ボタンが並んでいると、
  チェックのつもりで誤って削除・並べ替えをしてしまうため。
  編集モード中は行をタップしてもチェックが入らない
- 編集モード中は在庫ボタンと数値入力欄を出さない
  （1回きりの在庫リンクを無駄に消費させない・誤入力を防ぐ）

連動項目（`link` 付き）を開いて出てくる**子項目も編集できる**。子項目は
連動先エリアのものなので、追加・編集・削除・並べ替えはすべて
`sdef_<店舗>_customItems_<連動先エリア>` に対して行われる（中番側は変わらない）。
そのため `deleteItem` / `openEditDialog` / `openAddDialog` / `moveRoutineItem` は
エリアを引数で受け取れるようにし、省略時は今開いているエリアを使う。
ボタンには `data-rt-area` で対象エリアを持たせている。

- 編集中も連動項目は開閉できる（そうしないと子項目に触れないため）
- 並べ替えは追加項目のみ。組み込み項目（`AREAS` に定義があるエリアのもの）は
  並び順を持たないので上下ボタンを出さない。編集・削除はできる
  （編集は `itemEdits_`、削除は `hiddenItems_` に入る）

アイコンは `chevron-up` / `chevron-down` を新たに追加した。
`ic()` は未知の名前だと**空のSVGを返す**（エラーにならない）ので、
アイコンを使うときは `ICONS` に定義があるか確認すること。

### 2-5. 時間帯ごとに独立させた（担当者・チェック）

**担当者をシフトの出勤時間で分ける**

`routineHours()` の時間帯に出勤が重なる人を、その時間帯の担当者にする。

| タブ | 出勤時間 |
|---|---|
| 朝番 | 10:00-14:00 |
| 中番 | 14:00-19:00 |
| 遅番 | 19:00-23:00 |

タブを切り替えると担当者も切り替わる。通し勤務は全部に入る。
シフトが取れない日は担当者を空にせず、今の選択を保つ。
時間帯の定義は `const` だと定義行より前に呼ばれてエラーになるため、
巻き上げされる関数にしている。

**連動項目のチェックを時間帯ごとに分ける**

フロアは朝番・中番・遅番の3つが、シャワー・サウナ・トイレなども複数の時間帯が
同じエリアを `link` で参照している。`areaCompletionToday()` は
そのエリアの記録を時間帯に関係なく数えるため、**朝番でフロアを終わらせると
中番・遅番も完了扱いになっていた**（1日3回掃除する運用なのに）。

対策として「エリア@時間帯」という記録キーを導入した。

| | |
|---|---|
| 記録 | `clean_<店舗>_<担当者>_floor@routine_asa_<日付>` のように時間帯ごとに分ける |
| 定義 | `baseArea()` で `@` の前を見るので、項目一覧・見本・清掃方法は共有される |
| 入口 | `scopedArea(エリア, 開いている時間帯)`。やることリスト以外からは今までどおり |

- `getArea()` と `getGroups()` が `@` を落とすので、定義まわりは触っていない
- **エリア専用タブ（シャワールーム等）のチェックとは別の記録になる。**
  やることリストから入れたチェックはそちらには出ない
- 子項目の編集はベースのエリアに対して行う（`data-rt-area` はベース、
  `data-area` は記録用のスコープ付き）

### 2-7. エリアのタブから付けたチェックも、時間帯に振り分ける

2-5 で記録を「エリア@時間帯」に分けた結果、**エリアのタブ（シャワールーム等）から
直接付けたチェックが、朝番・中番・遅番のどれにも反映されなくなっていた**
（やることリストは `shower@routine_asa` を見るのに、タブ側は素の `shower` に書いていたため）。

`recArea()` を入れて、記録キーを作る所（`recordKey`）で時間帯へ振り分けるようにした。

| | |
|---|---|
| 振り分け先 | そのエリアを `link` で参照している時間帯のうち、**今より前に始まっている一番新しいもの** |
| 早朝など、どれも始まっていないとき | 参照している中で一番早い時間帯 |
| どこからも参照されていないエリア（マシンメンテ等） | 今までどおり時間帯で分けない |

例）笠寺のシャワーは朝番と遅番から参照 → 16:24 に触ると朝番ぶん。
萩野通のシャワーは朝・中・遅から参照 → 16:24 なら中番ぶん。
スタジオは中番だけが参照 → 何時に触っても中番ぶん。

**あわせて直した所**（2-5 で時間帯つきのキーを見落としていた集計）

| 場所 | 直し方 |
|---|---|
| `loadRecordMerged` / `areaCompletionToday` | その時間帯ぶん＋**時間帯で分ける前の同日の記録**も拾う（移行日にチェックが消えないように） |
| `areaLastCleaned`（最終清掃日） | 時間帯をまたいで数える |
| `storeDayProgress`（店舗まとめ） | 同上。分けたあと0件表示になっていた |
| `lastCheckedByItem`（前回いつ） | `baseArea` にまとめる |
| `needsProof` / `proofSpotFor`（抜き打ち撮影） | `baseArea` で判定。**2-5 以降、やることリスト経由のチェックで撮影が出なくなっていた** |
| 他の担当者のチェック取り消し | 時間帯つき→旧形式の順に探す |

記録キーの分解は `parseRecordKey()` に集約した
（`clean_<店舗>_<担当者>_<エリア>_<日付>`、店舗名・担当者名に `_` は無い前提）。

### 2-8. ゴルフのクラブ本数を男性・女性で分けて記録する

ゴルフA・ゴルフBに「クラブの本数確認」を追加した（`ga_clubs` / `gb_clubs`、
`ga16` / `gb16`「クラブ・備品の清掃・確認」の直後）。
数値入力は既存の `nums` の仕組みで、サーマナイフのショット数と同じ形。

```
"nums": [{"id": "m", "label": "男性"}, {"id": "w", "label": "女性"}]
```

- 保存先は `nums_<店舗>_<日付>` の `{"ga_clubs": {"m": "..", "w": ".."}}`。
  **項目idだけで引く（エリアは入らない）ので、A と B で別のidにしてある**
- 両方の欄が埋まった時点でその項目が実施済みになる。欠けると未実施へ戻る
- 清掃の `ga16` とは別項目にした。`nums` を `ga16` に足すと
  「清掃した」のチェックが本数を入れないと付けられなくなるため

**あわせた画面側の直し**: やることリストの子項目（`.rt-child`）に数値入力欄が
出ていなかった。ゴルフAは朝番、ゴルフBは中番から `link` で開くため、
このままでは本数欄が見えない。子行にも `numFieldsHtml()` を出し、
その連動先エリア（時間帯つき）に結びつけるようにした。

- 編集モード中は出さない（並べ替え中の誤入力を防ぐ）
- `.rt-child.has-nums { flex-wrap: wrap; }` で欄を次の行へ落とす
  （`.rt-row.has-link` と同じ手）

### 2-9. タブの数字を「実施した状態」に合わせる

朝番→中番のようにタブを切り替えると、**さっきまで残り1件だった朝番が
残り3件に戻って見える**ことがあった。

原因はタブのバッジだけが `loadRecord()`（＝いま選ばれている担当者の記録）を
見ていたこと。2-5 でタブを切り替えると担当者もその時間帯の出勤者に
変わるようにしたため、担当者が変わるたびに他のタブの数字まで動いていた。

`renderTabs()` の `makeTab` を `loadRecordMerged()`（その日・その店舗の全員合算）に変えた。

- 中の一覧も進捗バーも元から合算を見ていたので、**タブの数字とズレていた**。
  これで一致する
- 連動項目はもともと `areaCompletionToday()`（全員合算）で判定していたため、
  ズレていたのは手でチェックする項目だけだった
- 担当者を手で選び直しても数字は動かない

### 2-10. やることリストの行に説明文を出す

朝番・中番・遅番の行は**題名しか出しておらず、`desc` はどこにも表示されていなかった**。
そのため 2-4 で入れた「各項目どれか最低1つは必ず／3日で全て実施」や
「時間目安 14時／16時／18時」はスタッフの画面に届いていなかった。

`renderRoutine()` の行に2段目（`.rt-desc`）を足した。

- 説明文が空の項目には出さない（行の高さは変わらない）
- **編集モード中は出さない**（並べ替え中に行が伸びると押しにくいため）
- `.rt-row.has-desc { flex-wrap: wrap; }` で2段目へ落とす（`has-link` と同じ手）
- 連動項目の子行（`.rt-child`）は今までどおり題名だけ。
  細かい説明はエリアのタブで読む

### 2-12. マシンメンテを中番から開けるようにする（linkAny・区分の見出し）

「ジムエリア マシンメンテ」は手でチェックする1行だけで、**中番の画面からは
どこをやったのか分からなかった**（説明文が「マシンメンテのタブで実施」だけ）。
ゴルフ・スタジオと同じ連動項目にした。そのために画面側を2つ直している。

**1. `linkAny`（どれか1つ以上で完了）**

`linkedStatus()` は連動先が **100%完了** して初めて完了にする。
マシンメンテは「3日で全て実施」なので1日で全部そろう日が無く、
そのままだと中番が永久に終わらない（タブのバッジも0にならない）。

```
複数日で回す項目は  "linkAny": true  を付ける → 1つ以上チェックで完了
```

**2. 連動先を開いたときの区分の見出し**

マシンメンテは**区分をまたいで同じ題名が出る**（「マシン」がホコリ取りにも
拭き上げにもある）。平らに並べるとどれをやったのか区別できないため、
区分が2つ以上あるエリアは `.rt-subhead` を出すようにした。
シャワー・トイレなど組み込みエリアの展開も読みやすくなる。

- `getGroups()` が追加項目を組み立て直すとき **`linkAny` が落ちていた**ので持ち回すよう修正
  （`link` と同じ扱い）。テストで気づけた
- 子項目の並べ替え用の通し番号は `areaItems()` と同じ順のまま（区分をまたいで数える）
- 記録は 2-7 の `recArea()` により、**マシンメンテのタブと中番のどちらから
  チェックしても同じキー**（`machine_mente@routine_hiru`）に入る。二重管理にならない
- 各項目の「前回いつ」が子行に出るので、3日で回す運用の進み具合が読める

### 2-13. サウナマットも時間ごとに開けるようにする

「サウナ オレンジマット適宜確認」も連動項目にした（**萩野通のみ**）。

| | |
|---|---|
| 追加したエリア | `saunamat`「サウナマット」（icon=`shirt`）を `sdef_萩野通_customAreas` の末尾へ |

| 中番側 | `routine_hiru_saunamat` に `link=saunamat` を付けただけ |

- **`linkAny` は付けていない**（3つそろって完了）。14時・16時・18時は

  マシンメンテのように何日かかけて回すものとは扱いを分けている
- シャンプー類の曜日わけは**やらない**と決めた（1行のまま説明文で示す）。
  その日1種類しかやらないので、3項目に分けると残り2つが毎日未実施に見えるため

### 2-14. マシンメンテを曜日の枠（月・木／火・金／水・土）で分ける

スプレッドシートは同じ12項目が **月・木／火・金／水・土 の3列**に分かれていて、
「3日で全て実施」「チェックは一週間消さない」という運用。
アプリは12項目を1セットしか持っていなかったので、曜日の区別が出ていなかった。

エリアに `weekCycle: true` を付けると、そのエリアの記録を**曜日の枠ごと・週ごと**に分ける。

| | |
|---|---|
| 記録キー | `clean_<店舗>_<担当者>_machine_mente@routine_hiru#d1_<その週の月曜>` |
| 枠 | `d1`=月・木／`d2`=火・金／`d3`=水・土（`DAY_GROUPS`） |
| 日付 | **その週の月曜**（`weekAnchor()`）。月に付けた分が木にも残る＝「一週間消さない」 |
| 日曜 | どの枠にも属さない＝**全体の点検**。3枠とも操作できる |

**画面**

- やることリストを開くと3つの枠が縦に並ぶ（表と同じ並び）
- **今日の枠だけ白く操作可、他の枠は灰色で見るだけ**（押してもチェックは入らない）。
  灰色側にも今週やった分のチェックが見えるので、週の進み具合が読める
- 進捗（`n/12`）は**今日の枠だけ**を数える

**触った所**

- `baseArea()` が `#` も落とすように（`machine_mente@routine_hiru#d1` → `machine_mente`）
- `recArea()` に枠の付与を追加。`recDate()` を作り、
  `recordKey` / `loadRecordMerged` / `areaCompletionToday` の日付をここ経由にした
- 週で分けるエリアは `isWeekCycleArea()` で判定（`_weekCycleCache` は描画ごとにクリア）

**注意**: 記録キーの形が変わるため、この変更より前に付いていたマシンメンテのチェックは
画面に出なくなる（消えてはいない。`clean_..._machine_mente@routine_hiru_<日付>` に残っている）。

### 2-15. 「ふりかえり」画面（清掃の頻度のフィードバック）

チェックシート／結果の比較 と並ぶ3つ目のモードとして追加。
その店舗の直近14日の記録から、**よい所・気になる所・今後どうするか**を出す。

| 区分 | 中身 |
|---|---|
| 期間のまとめ | 記録のある日数／チェック数／記入した人数／時間帯ごとの日数 |
| よくできている所 | 実施日数の多いエリア上位5＋「直近7日で4日以上」の項目数 |
| 気になる所 | **間があいている**（3日以上）と**一度も記録が無い**を分けて出す |
| 今後どうしよう | 数字から自動で組み立てた提案（`reviewSuggestions()`） |

**設計で気をつけた所**

- **「間があいている」と「一度も記録が無い」を混ぜない。**
  混ぜると、そもそも使っていない組み込みエリアが「記録なし」で大量に並び、
  本当に見てほしい「5日あいているゴルフA」が埋もれる（テストで発覚）
- 「まだ一度もチェックされていない項目」は**使っているエリアの中だけ**数える。
  使っていないエリアは別の行で挙げているので二重に責めない
- **「記録が無い＝やっていない、とは限りません」**の注意書きを必ず出す。
  このデータで分かるのは実施の有無ではなく記録の有無
- 提案は必ず1つ以上出す（問題が無ければ「この調子で」）

記録は localStorage を直接読む（`parseRecordKey()` + `baseArea()`）ので、
時間帯（`@`）や曜日の枠（`#`）で分かれた記録もエリア単位でまとめて数える。

### 2-16. 抜き打ち実施写真（📷）の現状（2026-09 時点の本番設定）

「どの項目で写真を求められるのか／どのくらいランダムなのか」を後から追えるように、
本番の `proofPool` / `proofSpots` を読み取って確認した結果を残しておく。

| | 内容 |
|---|---|
| 対象 | `proofPool` に入っている **17エリア・73項目**だけ |
| 確率 | `PROOF_RATE = 20` → 対象の **1/20 ≒ 5%**。1店舗あたり1日おおよそ3〜4項目 |
| 判定式 | `hashStr(日付 + '|' + 店舗 + '|' + エリア + '|' + 項目id) % 20 === 0` |
| 撮影場所 | `proofSpots` の候補から `…+'|spot'` の同じハッシュで日替わりに1つ |
| 保持 | `PROOF_KEEP_DAYS = 60` 日で写真とログを自動削除 |

**乱数ではなく決定的なハッシュ**である点が肝心。

- 同じ日・同じ店舗なら、**誰が開いても・何回開いても同じ項目**が当たる（担当者では変わらない）
- 日付が変わると当たる項目が入れ替わる。店舗ごとに独立
- 均等に配られるわけではないので、1件の日もあれば8件の日もある
- `needsProof()` / `proofSpotFor()` は先頭で `baseArea()` を通す。
  時間帯（`@`）や曜日の枠（`#`）で当たり外れが変わってはいけないため

**対象外**：やることリスト（`routine_*`）の行そのもの、`machine_mente`、プールに無い項目。
ただし**やることリストの子行から打つチェックは対象**（`floor@routine_asa` → `baseArea` は `floor`）。

**あえてやっていないこと**：どの項目が📷対象かのバッジは事前に出さない。
見えると「その項目だけ丁寧にやる」逆インセンティブになるため。

**既知の未使用データ**：`proofSpots` にあってプールに無い4件
（`entrance:door` / `fitshape:grip` / `machine:strength` / `machine:strength_grip`）は
撮影場所だけ残っている状態で、当たることはない。動作に害は無いのでそのままにしてある。

### 2-17. 撮影頻度を項目ごとに変えられるようにする（管理画面）

「ここはもっと撮ってほしい」を管理画面（店舗まとめ）から設定できるようにした。

| | 内容 |
|---|---|
| 保存先 | kv `proofRates` = `{ "areaKey:itemId": 分母 }`（**3店舗共通**） |
| 分母 | 1/N の確率。`0`＝なし、`1`＝毎日必ず、`20`＝従来どおり約5% |
| 選択肢 | なし／通常(約5%)／多め(約10%)／かなり多め(約20%)／半分くらい(約50%)／毎日必ず |
| 既定値 | `proofPool` に入っていれば `PROOF_RATE`(20)、入っていなければ `0` |
| 判定 | `proofRateFor()` → `needsProof()` で `hash % N === 0`（N=1 は無条件） |

**設計で気をつけた所**

- **`proofPool` は残したまま、`proofRates` を上書きとして重ねる。**
  プールは「点検の採点に関わる項目」という意味を持つので消さない。
  頻度の指定はその上に乗るだけなので、プールを直せば指定の無い項目には効く
- **既定と同じ値を選んだら指定を消す**（`delete map[key]`）。
  設定を小さく保ち、あとでプールを変えたときに素直に反映されるようにする
- **プールに無い項目も頻度を上げれば対象になる。**
  「撮影場所だけ登録されていてプールに無い項目」（§2-16）も、ここから拾える
- **やることリスト（`routine_*`）は一覧に出さない。**
  `needsProof()` が最初に弾くので、出しても設定できない項目になってしまう
- 一覧は**3店舗の和集合**。店舗によって有る無いが違う項目には「（笠寺のみ）」と付ける
- 上部に**1日あたりの目安**（`proofExpectedPerDay()` ＝ Σ 1/N）を店舗別に出す。
  頻度を上げたときに現場の手間がどれだけ増えるかがその場で分かる
- エリアごとに `<details>` で畳む。全部開くと項目が数百行になるため
- **対象が1件でもあるエリアを先に並べる**（`sort` は安定なので各群の中は定義順のまま）。
  組み込みの `toilet` / `esthe` / `golf` などは男女別エリアに置き換わって
  対象0件のまま残るので、後ろに送らないと本命が埋もれる
- 目安の計算（`proofExpectedPerDay()`）は **`areaKey:itemId` で重複を落とす**。
  組み込みと同じキーの追加エリアや、組み込みと同じidの追加項目があると
  `allAreas()` / `areaItems()` が同じ項目を二度返し、目安が水増しされる

変更はその場で保存（`syncSet`）。選択欄が一瞬緑になって保存できたと分かる。

### 2-19. 見回りを「場所を選ぶ → その場所の清掃リスト」にする（linkTabs）

手書きの図のとおり、上に場所の選びボタン、下に選んだ場所の清掃リストを出す。
場所ごとにチェックが残り、別の場所を選ぶとその場所の状態に入れ替わる。

| | |
|---|---|
| 場所 | `sauna_b1..b3`（サウナ男A／男B／サウナ女）、`shower_b1..b4`（シャワー男1／男2／女1／女2） |
| 中身 | その店舗で**今見えているサウナ／シャワールームの項目を複製**（非表示・編集・追加を反映） |
| 連動 | 中番 `routine_hiru_v3_07` の link を7つのカンマ区切り＋ **`linkTabs: true`** |

**`linkTabs`（新しい項目の設定）**

`link` が複数あると今までは全部を縦に並べていた（マシンメンテ・見回りの2箱など）。
`linkTabs: true` を付けると、連動先を**選びボタン**にして選んだ1つ分だけ一覧を出す。

- ボタンには場所ごとの進み具合（`1/12`）が出る。全部済むと緑
- 選んでいる場所は `routineLinkTab[項目id]` に持つ（画面内だけ・保存しない）
- 編集モードでは今までどおり全部を並べる（項目を足す先が分かるように）
- `getGroups()` が追加項目を組み立て直すときに **`linkTabs` を落とさない**ようにした
  （`linkAny` で同じ落とし穴を踏んでいる。§2-12）

**なぜ場所を「別エリア」にしたか**

見本写真・清掃方法は **`エリア:項目id:種別`** で紐づいている（`mediaId()`）。
1つのエリアの中で区分を分けると項目idを変えるしかなく、
シャワー11項目・サウナ7項目に登録済みの見本写真が全部外れる。
場所を別エリアにすれば**項目idを元と同じにできる**ので、

```
mediaBaseArea('shower_b1') -> 'shower'   // _(m|w|b\d+)$ を落とす
```

の1行で元エリアの見本写真・清掃方法をそのまま引き継げる
（`toilet_m` → `toilet` の男女別と同じ仕掛けを広げただけ）。

**アプリ側の変更**

- `mediaBaseArea()`: `_(m|w)$` → `_(m|w|b\d+)$`。`golf_b` は `_b\d+` に当たらないので無傷
- `renderTabs()`: エリア定義の `hidden: true` はタブに出さない（場所は見回りの中だけで使う枠）
- `proofRateAreas()` / `proofExpectedPerDay()`: 隠しエリアは撮影頻度の一覧から外す
  （元エリアと項目idが同じで二重に見えるため）
- 場所の選びボタン（`.rt-place`）と `routineLinkTab` を追加

**朝番・遅番にも広げた（同日）**

萩野通は朝番・遅番だけ**サウナとシャワーが別項目**なので、それぞれに割り当てた。

| やることリスト | 項目 | 場所 |
|---|---|---|
| 朝番 | `routine_asa_v3_04` サウナ清掃 | サウナ3ヶ所 |
| 朝番 | `routine_asa_v3_05` シャワー清掃 | シャワー4ヶ所 |
| 遅番 | `routine_ban_v3_05` シャワー清掃 | シャワー4ヶ所 |
| 遅番 | `routine_ban_v3_06` サウナ清掃・マット交換 | サウナ3ヶ所 |

- 説明文の **「1チェック＝男女両方」は外した**（場所ごとに分けたので実態と合わない）。
  「マット・排水溝ネットの交換も。1チェック＝男女両方」は前半だけ残す
- 記録は時間帯ごとに分かれる（`shower_b1@routine_asa` / `@routine_hiru` / `@routine_ban`）

`proofPool` は**エリア単位**なので、連動先を `shower` から `shower_b*` に変えた時点で

**サウナ室そのものと、サウナ室のシャワーを分けた（同日）**

サウナ室には**シャワーもある**ため、次のように分けた。

| 何を | どこで | 場所 |

**笠寺にも同じ形を入れた（同日）**

|---|---|

| 朝番 シャワー清掃 | シャワー4ヶ所 ＋ サウナ室のシャワー3ヶ所＝7ヶ所 |

- 場所の**キーは店舗共通**（`shower_b1` など）だが、中身は `sdef_<店舗>_customItems_<場所>`
  なので店舗ごとに独立。笠寺の場所には**笠寺自身の**シャワールーム／サウナから複製した
- 笠寺は `itemEdits_shower` で5項目、`itemEdits_sauna` で3項目の題名を変えているので、
  複製にもその題名が入る（`getGroups()` と同じ順・同じ内容で組み立てている）
- 笠寺と萩野通で非表示にしている項目が違うため、項目数も違う
  （笠寺サウナは `coldbath` `floor` も非表示）
- `proofPool` は**店舗をまたいだ全体の設定**なので、萩野通で場所を足した時点で
  笠寺の場所も対象に入っている

**注意点**

- 項目の定義は**複製**なので、あとでシャワールーム側の項目を増やしても
  場所には自動では入らない。増やしたときは作り直しが要る
  （ワークフローは既存の場所とシャワールームの項目idがずれていたら中止する）
- 記録は `shower_b1@routine_hiru` のように場所ごと・時間帯ごとに分かれる
- 親行の進捗は7ヶ所の合計（`12/92`）。全部そろって完了
- 萩野通では `shower` / `sauna` を指すやることリストが無くなったので、
  タブから直接チェックした分は `clean_萩野通_<担当>_shower_<日付>`（時間帯なし）に入る。
  タブは見本写真・清掃方法を見る場所として残っている

### 2-20. ふりかえりを厚くする（9つの欄を追加）

「みんなが見に来る画面」にするため、読み物ではなく**一目で分かる形**を足した。

| 欄 | 何を見せるか | もとになるデータ |
|---|---|---|
| 今日はここから | 間があいている場所3つをチップで | `lastCheckedByItem()` |
| 月次点検で落とした所 | 90点テストで満点を落とした区分と、その後14日の清掃日数 | `inspection_<店舗>` の `rows[].cat/score` |
| 曜日のクセ | 曜日ごとの「記録のある日」の割合。時間帯ごとの穴も | 記録の日付 |
| やることリストの完走 | 朝/中/遅が全項目そろった日の数 | `withDate()` で過去日を判定 |
| たまにやる清掃 | 期限切れの定期清掃 | `periodicStatus()` |
| 数の記録 | クラブ本数・ショット数の前回比 | `nums_<店舗>_<日付>` |
| （畳）まとめ付け | 同じ分に10項目以上入った記録 | 記録の `time` |
| （畳）手順が未登録 | `method` も画像も無い項目の数 | `countMedia(id,'method')` |
| （畳）時間帯ごとの記録 | 1時間ごとの棒グラフと、記録の無い時間 | 記録の `time` |

**新しい道具: `withDate(日付, fn)`**

`loadRecordMerged()` などは `dateInput.value` を見て記録キーを決める。
過去の日を判定したいときは、表示日付を一時的に差し替えて既存の関数をそのまま使う。
キャッシュ（`_areaCompCache` / `_linkCache` / `_weekCycleCache`）も退避・復元する。
連動項目の自動完了まで含めて正しく数えられるので、
「やることリストの完走」を判定するのに使っている。

**設計で気をつけた所**

- **「今日はここから」は使っている場所を先に出す。**
  一度も記録が無い組み込みエリア（その店舗に無い設備かもしれない）が
  上位を占めて、本当に見てほしい「5日あいているゴルフA」が消えた（§2-15と同じ落とし穴）
- **人どうしを並べない。** 「山田120件／佐藤80件」は勤務日数の差が実力差に見えるので入れない
- **まとめ付けは責めない書き方にする。**
  「後からまとめて付けるのが悪いわけではありません」を必ず添える
- 曜日・時間帯の注記は**並べる数を上限つき**にする。
  全曜日ゼロなら曜日を並べず「この期間ずっと記録なし」と書く
- 気づきにくい3つ（まとめ付け・手順未登録・時間帯）は `<details>` で畳む。
  毎日見るものではないため

**点検の区分とエリアの結びつけ**は `RV_INSP_AREAS` で持っている
（シャワー→`shower*` / トイレ→`toilet*` / フロア・マシン→`floor`,`machine` / サウナ→`sauna*`）。
点検項目の区分を増やしたらここも足すこと。

### 2-21. チェックシートの一番上に1行だけ出す

ふりかえりに9つの欄を足したところ「思ったより役に立たない」となった。
理由は2つ。**読んだあとに何をするかが変わらない欄が多い**ことと、
**ふりかえりは開かないと見えない**こと。
（実績では萩野通は30日中4日しか記録が無い。使われていない画面に
分析を足しても、その画面自体が使われない）

そこで、**みんなが毎日開くチェックシートの一番上**に1行だけ出すようにした。

```
⚡ 今日は ゴルフA（5日あいています）      ← 押すとそのエリアが開く
```

- 中身は `rvTodo3()` の1番目（いちばん間があいている場所）
- **一度も記録が無い場所は出さない**（その店舗に無い設備かもしれない）
- 全部片付いていれば緑で「今日ぶんはひととおり回っています」
- `render()` の冒頭で毎回引き直すので、チェックした瞬間に次の場所へ変わる
- やることリストの画面でも出る（`render()` が早期 return する前に呼ぶ）

**教訓**：分析を増やすより、**一番効く1つを、みんなが必ず見る場所に置く**ほうが
実際の行動は変わる。ふりかえりは「次の点検、大丈夫そう？」に答える所に絞る。

### 2-22. 端末間の同期（同じ店舗でiPadを2台使う）

**症状**：同じ店舗でiPadを2台使うと、片方で付けたチェックがもう片方に出ない。

**原因**：`bootstrap()` は**起動時に1回だけ**サーバーから全部を読む。
`syncSet()` は書き込みをサーバーへ送る。
つまり**送るだけで、あとから取りに行く経路が無かった**。
`visibilitychange` でも版の確認と日付の繰り上げしかしていなかった。

**直し方**：サーバーに「変更の通し番号」を持たせ、端末は変わったキーだけ取りに行く。

| | |
|---|---|
| サーバー | `stateRev`（通し番号）と `changeLog`（上限800件・メモリ内） |
| `PUT/DELETE /api/state/:key` | 値が実際に変わったときだけ番号を進め、`rev` を返す |
| `GET /api/changes?since=N` | `N` 以降に変わったキーと消えたキーだけ返す |
| `GET /api/state` | `rev` も返すようにした（起点を知るため） |

`since` が古すぎる／サーバーが再起動した場合は **`full: true`** を返し、
端末は `/api/state` を取り直す（`changeLog` はメモリ内なので再起動で消える）。

**待ち受けにした（20秒 → 0.1秒以下）**

20秒ごとの取りに行きでは遅いので、`/api/changes?wait=1` を
**変化があるまでサーバー側で待つ**形にした（ロングポーリング）。

- サーバーは `waiters` に待っている端末を持ち、`bumpRev()` で一斉に返す
- 何も起きなければ **25秒**で空返し（fly のプロキシに切られない範囲）
- 端末は返ってきたらすぐ次を張る（`longPollLoop()`）
- **画面を見ていない間は止める**（`stopLongPoll()`／`document.hidden`）。通信と電池の節約
- 変化なしですぐ返ってきた場合は1.5秒置いてから張り直す（つなぎ直しの暴走防止）
- 30秒ごとに立て直しの `setInterval`（接続が切れたまま止まらないように）

`min_machines_running = 0` / `auto_stop_machines = true` だが、
**画面を開いている間はどのみちサーバーが起きている**ので、
速くしても止まる時間は変わらない（＝費用は変わらない）。

**端末側**

- **待ち受け**＋**画面に戻ったとき**＋**ウィンドウにフォーカスが戻ったとき**に `pullChanges()`
- 全部（`/api/state` は約1MB）は毎回引かない。変わったキーだけ
- **送信できていない自分の変更（`pendingSync`）はサーバーの値で上書きしない**
- 自分が書いた直後は `PUT` が返す `rev` で番号を進め、自分の変更を引き直さない
- **入力の最中は画面を作り直さない**（`canRefreshNow()`：ダイアログが開いている／
  input・select・textarea にフォーカスがある間は表示の更新だけ見送る。データは取り込む）
- 反映は今開いている画面だけ（チェックシート／店舗まとめ／ふりかえり／結果の比較）

**確かめたこと**（`test-twodevice.js`）：2台で同じ店舗を開き、
片方のチェック・取り消しがもう片方に出ること、やることリストの進み具合が揃うこと、
サーバーを再起動しても追いつけること。

### 3. 在庫システムへログインなしで移れるようにした

在庫システム（`inventory-system-aburiva.fly.dev`）の `GET /enter` は、両サイトで共有した
合言葉から作った HMAC-SHA256 の署名を検証して、ログイン画面を飛ばす。
「どこから来たか」の判定に Referer は使わない（送る側が自由に書ける値のため）。

| 項目 | 内容 |
|---|---|
| 発行API | `POST /api/inventory-link`（`/api` の保護の内側。未ログインは401） |
| 署名対象 | `loc=..&user=..&exp=..&nonce=..` の順。値は `encodeURIComponent` 済み |
| 有効期限 | 発行から5分（在庫システム側の上限は10分） |
| 使用回数 | 1回きり。押されるたびに作り直す。保存も使い回しもしない |
| 画面 | 朝番・中番・遅番の「在庫管理システムを開く」ボタン（押した時に発行） |

必要な環境変数（Fly secrets）:

| 変数 | 内容 |
|---|---|
| `INVENTORY_LINK_SECRET` | 在庫システムと共有する合言葉。**未設定だと発行せず503を返す** |
| `INVENTORY_ACCOUNTS` | 店舗→拠点の対応。`{"笠寺":{"loc":"..","user":".."},...}` |
| `INVENTORY_BASE` | 在庫システムのURL（省略時 `https://inventory-system-aburiva.fly.dev`） |

守っている決まり:

- 合言葉はサーバーの環境変数からのみ読む。コードにも設定ファイルにも書かない。
  ブラウザにも渡さない（渡すと誰でも自前でリンクを作れて、ログインを迂回できる）
- 拠点はサーバーが決める。店舗合言葉の端末は他店舗のリンクを作れない
  （マスター合言葉のセッションだけ、どの店舗で入るかを選べる）
- 発行APIは **POST**。GETにすると `SameSite=Lax` のクッキーがトップレベル遷移で送られ、
  外部サイトからログイン済みスタッフを勝手に飛ばせてしまう
- 発行したURLはログに出さない

### 合言葉の配り方

**使用方法PDF（`/usage-guide.pdf`）に合言葉を載せてはいけない。**
`public/` の中身は `express.static`（`server.js`）がそのまま配っていて、
保護しているのは `app.use('/api', ...)` の `/api/*` だけ。つまりPDFは
認証なしで誰でも取得できる。デプロイ時の検証でも同じ実行の中で
`/usage-guide.pdf` は 200、`/api/state` は 401 になることを確認している。

代わりに、印刷用の合言葉シート（A4・1枚×3店舗）をワークフローで作る。

| | |
|---|---|
| ワークフロー | `store-password-sheet.yml`（`pw-sheet.txt` を更新すると走る） |
| 出力 | アーティファクト `store-password-sheets`。7日で消える |
| 中身 | 店舗名・合言葉・使い方3行・取り扱いの注意 |

合言葉は本番の環境変数から読み、`::add-mask::` でログに出ないようにしている。
`gym-reservation-system` は非公開リポジトリなので、アーティファクトを取れるのは
リポジトリを見られる人だけ。

シートには「この合言葉で在庫システムにも入れる」と明記してある。連携した以上、
清掃管理表の合言葉の重みが上がっているため。

### 残っている弱点（未対応・要検討）

この仕組みの強さは「清掃管理表のログインと同じ」まで。以下は今回直していない。

| 内容 | 場所 |
|---|---|
| `/api/login` `/api/admin-login` に総当たり対策がない | `server.js` |
| `BASIC_PASS` 未設定だと `/api/*` の保護が丸ごと外れる（リンク発行APIだけは503で防いである） | `server.js` |
| 合言葉の比較が短絡比較（`===`）。`timingSafeEqual` が望ましい | `server.js` |
| 認証クッキーが全員共通・1年有効のため、個人の識別も端末単位の失効もできない | `server.js` |

最後の1つのため、在庫システムに渡す `user` は**店舗ごとの固定ID**にしている。
個人名を渡しても本人確認された値にはならないため。

### 2-23. 在庫システムに担当者の名前を渡す

**症状**：在庫管理を開くと、名前がいつも「清掃管理表」になる。

**原因**：在庫システムへのリンクに乗せている `user=` は、
向こうの**ログインアカウントのID**として引かれる（`users` テーブル）。

```
SELECT * FROM users WHERE location_id = ? AND user_id = ?
```

見つかった行の `user_name` がそのまま画面の名前になる。
店舗ごとに「清掃管理表」という**共用アカウントが1つ**あって、全員がそれで入っていた。
`user=` に担当者の名前を入れても「そんな利用者はいない」で弾かれる（＝ログイン画面に飛ぶ）。

**直し方**：署名する項目に `by`（操作者名）を1つ足す。

```
/enter?loc=..&user=清掃管理表&exp=..&nonce=..&by=山田&sig=..
                                              ~~~~~~~~ これも署名の対象
```

| | |
|---|---|
| `user` | 入る権利。これまで通り共用アカウント |
| `by` | 誰が触っているか。チェックシートの担当者をそのまま渡す |

`by` は**あってもなくてもよい**。無ければ署名の元にも入らないので、
2つのシステムを同時に入れ替えなくてよい。ただし**署名の対象ではある**ので、
URLの `by` を書き換えても剥がしても後から足しても、署名が合わずに弾かれる。

**両方直す必要があった**

| | 直す前 | 直した場所 |
|---|---|---|
| 画面の表示 | `ログイン中: 清掃管理表` | 在庫システムの `entry.js` |
| **記録に残る名前** | 出庫履歴・発注・棚卸が全部「清掃管理表」 | `operator_name` 列を追加 |

在庫システムの履歴は `SELECT user_name FROM users WHERE id = ?` で名前を出していたので、
**画面だけ直すと「画面は山田さん、履歴は清掃管理表」**になる。
記録の行に `operator_name` を足し、表示は「行の名前が先、無ければアカウント名」にした。
列を足す前の記録と、普通にログインして入力したぶんは空のままで、これまで通り出る。

**デプロイの順番（大事）**

**在庫システムを先に出す。** 逆にすると、
清掃管理表が `by` 込みで署名したリンクを、`by` を知らない在庫システムが
`by` 抜きで検算するので**署名が合わず、リンクが開けなくなる**。

- 在庫システムが先：`by` の無い古いリンクもそのまま通る（何も壊れない）
- 清掃管理表が先：**リンクが全部ログイン画面に飛ぶ**

**この側（清掃管理表）の変更**

- `server.js` の `/api/inventory-link`：本文の `by` を受け取り、署名に含める。
  名前として読めない値（40字超・`< > " ' & \` や制御文字）は**付けずに**発行する
  （付けて向こうに弾かれると、リンク自体が開けなくなるため）
- `public/index.html`：`openInventorySystem()` が `staffSelect.value` を一緒に送る

**注意**：署名の元になる文字列は2つのリポジトリで別々に組み立てている。
`['loc','user','exp','nonce']` の順、`by` があれば最後、という並びが
在庫システムの `server/services/entry-link.js` と揃っている必要がある。

### 2-24. 萩野通の水素水を別エリアにする

**やりたかったこと**：萩野通の水素水だけ中身を変えられるようにする。

**なぜできなかったか**：3店舗が**同じ組み込みエリア `hydrogen`** を使っていた。
`sdef_<店舗>_hiddenItems_*` などは店舗ごとに持てるが、
「萩野通にだけ項目を足す」ことはできても**エリアそのものを分けることはできない**。

**やったこと**（データのみ。デプロイなし）

| | |
|---|---|
| 1 | 追加エリア `hydrogen_haginodori`「水素水サーバー（萩野通）」を萩野通に作る |
| 2 | 今出ている5項目（組み込み `tray`/`body`/`floor` ＋ 追加2件）を**並び順・手順ごと**複製 |
| 3 | 萩野通の `hydrogen` は**全項目を非表示**に。組み込みエリアは項目0件でタブから外れる |
| 4 | 中番「水素水サーバー本体の拭き上げ」の連動先を新エリアへ |
| 5 | `proofPool` に新エリアを追加 |
| 6 | 見本写真・清掃方法の画像8枚を複製 |
| 7 | 萩野通の `clean_` 記録を新エリアのキーへ複製 |

**項目idはわざと同じにしてある**（`tray` / `floor` / `c178065165889019` …）。
そうすると `proofPool` も見本写真も**キーの前半を差し替えるだけ**で写せる。

**忘れると壊れるところ（2つとも実際にハマった）**

- **`proofPool`**：新しいエリアを入れ忘れると、そのエリアだけ抜き打ち写真が来なくなる。
  §2-19 のブースのときと同じ罠。
- **記録の引き継ぎ**：エリアを分けただけだと記録が古いキーに残る。
  **今日すでに付けたチェックが消えたように見える**し、`rvTodo3`（今日はここから）や
  たまにやる清掃が「最後にやった日」を見失って、**ずっと未実施あつかい**になる。
  古いキーは消していない（タブから外れていて誰にも見えないため）。

**見本写真は共有ではなく複製にした**

`mediaBaseArea()` は `_(m|w|b\d+)$` しか剥がさないので、`hydrogen_haginodori` は
元エリアの写真を引き継がない。正規表現を広げて**共有**にする手もあったが、
別の機械にするためにエリアを分けたので、**複製して別々に育てられる**ようにした。

**進め方**

読み取りのみの調査 → 手元で作りものの state を使ってテスト（定義23件・記録9件）→
変更前の値をアーティファクトに残して適用 → 適用後に本番のデータを取り直して確認
（他店舗が1バイトも変わっていないこと、画像を1枚も失っていないことを含む）。

**同じことを他店舗でやる場合**は、`hydrogen` を対象にしたこの手順がそのまま使える。
`STORE` / `NEW` / `NEW_NAME` と、連動している「やることリスト」の項目idを差し替える。

### 2-25. 進捗バー：8割に届かないときは赤く出す

**やりたかったこと**：やることの8割くらいはやってほしいので、届いていなければ一目で分かるようにする。

**分母を変えた**

やることリストの「0 / 17」の **17 は行数**だった。だがその中の1行「シャワー清掃」は
実際には7ヶ所ぶんの作業を指している。**行数で数えると実際の作業量よりずっと小さく出る**ので、
**連動先の中身の数**で数えるようにした（`routineProgress()`）。

| 行の種類 | 数え方 |
|---|---|
| 連動なし | 1件 |
| 連動あり | **連動先の項目数**（「シャワー清掃」1行 = 7ヶ所ぶん） |
| `linkAny`（どれか1つやれば完了） | **1件**。中身で数えると全部そろう日が無く、永久に埋まらない |
| 連動先にまだ項目が無い | 1件（行そのもの） |

同じ連動先を2行が指していても二重に数えない（`seen` で除外）。
普通のエリアのバーはこれまで通り、そのエリアの項目数。

**0%のとき緑のバーは幅ゼロで見えない**

`.progress-bar` に赤を付けるだけだと、**0% では幅が0なので何も見えない**。
`.progress-bar-wrap`（下地）にも `.under` を付けて薄い赤にしている。

**目標の位置に細い線**

赤いだけでは「どこまでやれば赤が消えるのか」が分からないので、
`::after` で 8 割の位置に線を引いた。位置は `--target` に JS が入れる
（`PROGRESS_TARGET` と必ず一致させるため。CSS側に数字を書くと片方だけ直す事故になる）。

**シャワーは分母に入れない**

シャワーは場所が7ヶ所あり、中身を全部数えると**98項目**（笠寺・萩野通）。
これを分母に入れると他のやることが数字の中に埋もれるので、
`isShowerArea()`（`shower` / `shower_b1..b7` / `shower_round`）を分母から外した。
シャワーだけを指している行（「シャワー清掃」「シャワーの見回り清掃」）は
**行ごと数えない**。進み具合は場所の選びボタンの数字と、シャワーのタブのバーで見る。

**サウナは外していない**（部屋数が少ないため）。ただし萩野通・笠寺の朝番では
サウナ3室で**30項目**あり、分母の約4分の1を占めている。

**本番の実際の分母**（2026-09-10 時点）

| 店舗 | 朝番 | 中番 | 遅番 |
|---|---|---|---|
| 笠寺 | 122 | 58 | 67 |
| 枇杷島 | 100 | 59 | 66 |
| 萩野通 | 113 | 60 | 74 |

朝番だけ突出して重い（サウナ30＋トイレ22＋ゴルフ21＋パウダー18…）。
番によって重さが違うので、8割という同じ目標が全部に合うとは限らない。

**中番を1人で回しているときは 65%**

**まだ揃っていないところ**：店舗まとめ・比較の `ratioClass()` は

### 2-26. 過去の日付を見るときの担当者

**症状**：過去のデータを見ると、担当者が**今日の出勤者**になってしまう。

**原因は2つ**

1. 日付を変えても `currentStaff` を変えていなかった。
2. `autoSelectShiftStaff()` が**毎分**走り、`onShiftCombined()`（＝`todayStr()` の
   シフト表を見る）で担当者を上書きしていた。過去日を見ている最中でも走るので、
   仮に手で選び直しても1分以内に今日の出勤者へ戻されていた。

チェックの中身は `loadRecordMerged()` が店舗ぶんを合算しているので正しく出ていた。
**ずれていたのは名前だけ**。

**直し方**：表示している日付で担当者の決め方を分ける。

| 見ている日 | 担当者 |
|---|---|
| 今日 | シフト表の出勤者（これまで通り） |
| 過去 | **その日にそのエリアの記録を残した人**（記録の多い順で1人） |

- `staffWithRecords(date, areaKey)` … その日に記録を残した人を、記録の多い順に返す。
  やることリストのときは**連動先の記録も**自分のものとして数える
  （`toilet_m@routine_ban` は遅番のもの）
- `syncStaffForView()` … 日付を変えたとき・タブを変えたときに呼ぶ。今日に戻れば
  保存してある担当者に戻してからシフトの自動選択をやり直す
- `applyShiftStaffForArea()` と `autoSelectShiftStaff()` の先頭で `isPastView()` を見て
  何もしない（**どの経路からも上書きされない**ようにするため）

**エリアごとに担当者が変わる**。同じ日でもトイレは佐藤、ゴルフAは山田、というように
実際に記録した人が出る。記録が1件も無い日は「担当者未選択」のまま（今日の出勤者は出さない）。

**保存しない**

過去日ぶんの担当者は `localStorage` に書かない。書くと今日に戻ったときに
引きずるうえ、`currentStaffDay` による共用端末対策（日付が変わったら担当者を
リセットする仕組み）とも噛み合わない。

**名簿から外れた人**も、その日の記録があれば選択肢に出るようにした。
退職者がやった日の記録が開けなくなるため。

### 2-28. 端末間の同期が、画面に触れていると止まる

**症状**：iPadを2台使っていると、パーセント（進捗バー）が相手の端末に追いつかない。

**原因**：`canRefreshNow()` が広すぎた。

```js
if (a && /^(INPUT|SELECT|TEXTAREA)$/.test(a.tagName)) return false;
```

打ちかけの文字が消えるのを防ぐための番人だが、**`select` まで「入力中」に数えていた**。
iPadでは担当者の選択欄をタップしてピッカーを閉じたあとも、**焦点が `select` に残る**。
その間ずっと `refreshAfterPull()` が入口で戻され、チェックもパーセントも更新されない。

**しかも見送った更新を捨てていた。** 取りに行った中身はもう `localStorage` に入っているので、
**次に何か変わるまで誰も描き直さない**。画面を触るまで古いまま固まる。

**直し方**

| 触れているもの | 更新 |
|---|---|
| `textarea` / 文字・数字を打つ `input` | **見送る**（打ちかけが消えるため） |
| `select` / `date` / チェックボックス等 | **する**（描き直すのは一覧とタブだけで、選択欄には触らないため） |
| ダイアログが開いている | 見送る |

見送ったぶんは `pendingRefresh` に覚えておき、
**焦点が外れた・画面に触れた・3秒ごとの保険**のいずれかでやり直す。
`select` に焦点があるときは描き直しはするが、**選択肢の作り直しだけ**は先送りする
（開いているピッカーが閉じるため）。

**再現のしかた**：ブラウザの窓を2つ開き、片方で選択欄に焦点を当てたまま、
もう片方でチェックを付ける。`scratchpad/repro-sync2.js` がそれを自動でやる。

### 2-34. 水素水に「モニターチェック」（笠寺・枇杷島）

`hydrogen_monitor`「モニターチェック」を、水素水サーバーの**追加項目の末尾**に足した。

| | |
|---|---|
| 題名 | モニターチェック |
| 説明 | 映像が正常に流れているか確認 |
| 手順 | ①電源が入っているか ②映像が止まらず流れているか ③映っていなければ報告 |

増えない／題名だけ同じ行がある／非表示に残っている／行が読めない、の5通り）→
変更前の値をアーティファクト `hydrogen-monitor-before` に残して適用 → 適用後に
本番のデータを取り直して確認（萩野通・共通キー・`proofPool` が1バイトも変わっていないこと含む）。

- **ボタンは、いい例か悪い例が登録されている項目にだけ出す**。

**気をつけたところ**

  `baseArea()` で時間帯・曜日枠を落としてから `mediaBaseArea()` に渡す。

### 2-36. 「項目を編集」（ペン）から、いい例・悪い例の写真を登録できるようにする

やることリストの編集モードに出る**ペン**から見本写真を登録したい、という依頼。
編集ダイアログに「いい例・悪い例の写真を登録する」ボタンを足し、押すと
これまでの見本ダイアログ（OK例／NG例の登録）が開くようにした。

- ボタンには今の登録数が出る（`OK 1` `NG 1` / 何も無ければ「（未登録）」）。
- 見本ダイアログを閉じても**編集ダイアログは開いたまま**（`fromEdit` のときは裏の画面を描き直さない）。
- 登録すると、その項目のチェックの右に「例を見る」が出る。

**見本写真の登録がそもそも動いていなかった（本番も同じ）**

`compressImage` という**同じ名前の関数が2つ**あった。

| 行 | 中身 | 呼ぶ側 |
|---|---|---|
| 約2396 | `compressImage(file)` … 1600px/0.82、小さい画像はそのまま | `addMediaFile`（見本・清掃方法の写真） |
| 約2815 | `compressImage(file, maxSide, quality)` … 抜き打ち写真用 | 撮影の処理 |

関数宣言は**あとの定義が勝つ**ので、`addMediaFile` は引数なしで下の方を呼んでいた。
`maxSide` が `undefined` → 倍率が NaN → キャンバスが 0×0 → `toBlob` が null →
`compress failed` で落ち、**写真が1枚も保存されない**。回収した元の版にも入っていたので、
抜き打ち写真の機能を足したときから、見本の登録はずっと失敗していたことになる
（それ以前に登録されたものは残っている）。

下の方を **`compressToJpeg`** に改名して直した。

**保存先のエリアを指定できるようにした**

`addMediaFile` は `currentArea` をそのまま鍵の先頭にしていたが、
読み出し側（`mediaIdsForArea`）は `baseArea` → `mediaBaseArea` でそろえている。
やることリスト（`routine_asa`）や男女別エリア（`toilet_m`）から登録すると鍵がずれて、
**登録できても表示されない**。`addMediaFile(..., areaKey)` と
`renderGalleryInto(..., areaKey)`、`openMediaDialog(item, areaKey, fromEdit)` を足し、
読み出しと同じそろえ方に統一した。

- 連動先の子項目（例: サウナ清掃の中の行）→ `sauna:...`
- やることリストそのものの行 → `routine_asa:...`

**やることリストの親の行にも「例を見る」を出した**。そこで登録した見本が
どこにも出ないままになるため。`.rt-row` も開閉の対象に入れている
（最初 `.item, .rt-child` しか見ておらず、親の行だけ開かなかった）。

### 2-37. 比較の「全体」を直し、タブを1行にまとめる

**「全体」のパーセントが他の列と合っていなかった**

比較の表の「全体」は**保存時の合計をそのまま**出していた。ところがエリアの列は
2-32 で「時間帯をまたいだ記録をまとめて数える」ようにしてある。
同じエリアを朝番と中番の両方で触ると、**全体だけ二重に数える**ので合わない。

```
トレーニングフロアを朝番で3件・中番で5件チェックした人
  全体          8 / 26 （31%）  ← 同じエリアを2回ぶん数えている
  トレーニングフロア 5 / 13       ← 重複を除いた数
```

「全体」も各エリアの列と同じ数え方（`itemDoneMap`）で足すようにした。
**列の合計と必ず一致する**。連動している項目が多いので、かなりの行で起きていたはず。

**上のバーとは、そもそも数え方が違う**（こちらは直していない）

画面上部の「78 / 97 完了 (80%)」は `routineProgress` で、
シャワーを分母から外し、「どれか1つやれば完了」の行を1件として数える（2-25・2-26）。
比較の表は記録された項目をそのまま数える。**この2つは一致しない**。

**タブを4つだけにした**

上段（清掃エリア）と下段（朝番・中番・遅番）の2行あったのを、1行4つにした。

```
朝番 / 中番 / 遅番 / 定期清掃
```

- 清掃エリアのタブは出さない。やることリストから開けて、例も行の中で見られる（2-35）ため。
- **エリアの追加**と、**どのやることリストからも連動していないエリアへの入口**は
  「店舗まとめ」（管理者）の中の**エリアの管理**に移した。タブから消すと行き場が
  無くなるエリアが出るため（`unlinkedAreas()` = `routinesLinking` が空のもの）。
  連動していないエリアが無ければ「ありません」と出る。
- **定期清掃はタブからの入口がここだけ**なので残す。
- やることリストが1つも無い店舗では、タブが定期清掃だけになってしまうので、
  そのときだけ清掃エリアのタブも出す。
- 最初に開く画面を `defaultArea()` にした。やることリストがあれば**時計に合わせて**
  その時間帯（朝番・中番・遅番）を開く。これまでは `AREAS[0]`（シャワールーム）だったが、
  エリアのタブが出なくなるとタブの無い画面から始まってしまうため。
- エリアを削除したあとの戻り先も `defaultArea()` にした。

### 2-38. 比較の列から、やることリスト（朝番・中番・遅番）を外す

2-37 で「全体」を列の合計に合わせたが、**その列の中に朝番・中番・遅番そのものが
入ったまま**だった。やることリストの1行は「シャワー清掃」のように**清掃エリアへの
入口**になっているものが多く、その行が終わるのは中のエリアが終わるとき。
つまり**同じ仕事を2回数えて**いて、しかもやることリストの側が件数で勝つので、
清掃エリアの割合がそちらに持っていかれてしまう。

```
シャワールームを21/23までやった人（枇杷島）
  全体        28 / 40  ← 朝番17件ぶんに引っ張られている
  朝番        7 / 17
  シャワールーム 21 / 23
```

比較の概要に出す列を `compareAreas()`（= やることリスト以外）にした。
店舗まとめの `storeDayProgress` も前から同じ考え方でやることリストを外している。

**やることリストだけの仕事は捨てない**

やることリストには「電源・開錠」「ゴミ出し」のように**どの清掃エリアにも
連動していない**行もある。これを落とすと、その日やることリストだけ触った人が
「-」になってしまう（本番の枇杷島に実際にそういう記録があった）。

連動していない行だけを集めて **「その他のやること」1列**にまとめ、「全体」にも入れる。
連動している行は今までどおり数えない。これで**全体＝並んでいる列の合計**が保たれる。

- `soloRoutineTitles(cols)` … `link` が空、または連動先が列に無い行を集める。
  鍵は「やることリストの鍵＋改行＋項目名」。朝番と中番に同じ名前の行があっても別に数える。
- `soloRoutineCount(h, titles)` … その回に記録されたぶんを数える。
- 連動していない行が1つも無い店舗では、この列そのものを出さない。

**店舗に無い設備の列も出さない**

ついでに、組み込みエリアで項目を全部消したもの（＝その店舗に無い設備）を列から外した。
タブの `visibleAreas()` と同じ判断。ただし `hidden:true` のエリアは外さない
（やることリストの連動先として記録が入る枠のため）。
**記録が残っているエリアは、項目が空でも列に残す**（過去のぶんが見えなくなるため）。

やることリストの中身を項目ごとに見たいときは、チェックシートの選択肢に
「朝番（やることリスト）」として残してある（清掃エリアの後ろにまとめた）。

### 2-39. 数値の「前回」が1日ずれていた（昨日のぶんを必ず飛ばす）

サーマナイフのショット数の下に出る「前回 09-09: 6700 (-1370)」が、
**前日（09-12）を飛ばして**その前の記録を出していた。値そのものは保存できている
（本番の `nums_枇杷島_2026-09-12` に `{"m":"5530","w":"8223"}` が入っている）。

原因は日付をずらすところ。

```js
const base = new Date('2026-09-13' + 'T00:00:00');   // = 09-12T15:00Z（日本時間のため）
new Date(base.getTime() - 1 * 86400000).toISOString().slice(0, 10)
//  → '2026-09-11'   ← 昨日（09-12）ではない
```

`new Date('...T00:00:00')` は**その場所の時刻**として読まれるが、`toISOString()` は
**世界標準時**に直す。日本時間は+9時間なので、1日引いた時点で日付が2日前になる。
120日ぶん遡る間ずっと1日ずれるので、**昨日の記録は一度も見ない**。

本番の枇杷島がちょうどこの形だった。

| 遡る | 出る日付 | あるもの |
|---|---|---|
| 1日前 | 09-11（本当は09-12） | ゴルフのみ → 外れ |
| 2日前 | 09-10 | ゴルフのみ → 外れ |
| 3日前 | 09-09 | サーマナイフ → **これを「前回」にしてしまう** |

`shiftDate(dateStr, days)` を足して、画面と同じ「その場所の日付」で組み立てるようにした。
`setDate` を使うので月またぎ・年またぎも正しい。

なお `Date.now() - N*86400000` で作っている**保存期間のしきい値**（抜き打ち写真の
保持日数など）も同じだけずれるが、こちらは**1日長めに残る**方向なので直していない。

### 2-40. 残りが少なくなったら知らせる（サーマナイフのショット数）

数値の記録欄に、残りが少ないときの知らせを足した。

- `numLow` を下回る → **枠が赤くなる**（サーマナイフは2000）
- `numOut` を下回る → 枠が赤くなり、**「◯◯を交換してください（残り1000を切りました）」**と出る

**基準は項目ごとに持たせている。** 全部の数値欄に同じ基準を当てると、
ゴルフのクラブ本数（7〜11本）が常に「交換してください」になってしまう。
基準を入れていない項目は今までどおり何も出ない。

項目の編集（ペン）に入力欄を2つ足したので、**あとから現場で変えられる**。
空にすれば知らせは止まる。

「下回る」は `<` なので、ちょうど2000・ちょうど1000ではまだ切っていない扱い。
欄が複数あるときは、切った欄だけ赤くして、名前をまとめて1行に出す
（例：「男性・女性を交換してください」）。

**このとき見つけた不具合**

- `itemNumLimits` が、基準を入れていない項目（`undefined`）を **0 と読んでいた**。
  `String(undefined)` は `'undefined'` で空文字ではないため、空欄の判定をすり抜けていた。
- `getGroups` が項目を組み立て直すときに `numLow` / `numOut` を**載せ忘れていた**ので、
  保存しても効かなかった。組み込み項目（`edits`）・追加項目（`customItems`）の両方に足した。
  **`getGroups` は項目の中身を明示的に並べて作り直している**ので、
  項目に新しい設定を足すときはここも直すこと。

**本番に入れた基準（2026-09-13）**

| 店舗 | 項目 | numLow | numOut | 数値欄 | 遅番の項目数 |
|---|---|---|---|---|---|
| 笠寺 | サーマナイフショット数確認 | 2000 | 1000 | 男性・女性 | 17件のまま |
| 枇杷島 | 〃 | 2000 | 1000 | 男性・女性 | 16件のまま |
| 萩野通 | 〃 | 2000 | 1000 | 男性・女性 | 19件のまま |

変更前の控えは Actions のアーティファクト `knife-limits-before`（run #57）にある。
他の項目・他のキーは触っていないことを run #58 で確かめた。

**合言葉の要る操作をCIからやる方法**

`CLEANING_APP_PASSWORD` は**未登録**なので、CIから直接APIは叩けない。
かわりに**処理そのものをマシンの中で動かす**。マシンの中には `BASIC_PASS` が
環境変数で入っているので、localhost のAPIを叩けばよい。合言葉はCIに渡らず、
ログにも残らない。

```bash
B64=$(base64 -w0 fix.js)
flyctl ssh console -a "$APP" \
  -C "sh -lc 'echo $B64 | base64 -d > /tmp/fix.js && node /tmp/fix.js; rc=\$?; rm -f /tmp/fix.js; exit \$rc'"
```

base64 で渡すのは、日本語やクォートが `ssh -C` の途中で壊れないようにするため。
アプリは**ポート3000**で動いている。

### 2-41. 定期清掃に「次にやる日」を足し、今日ぶんを plus α に出す

**たまにやる仕事の登録先は定期清掃ひとつ。** チェックシートの下に
「今日の plus α」として出る。

- 定期清掃に**「次にやる日」**を足した。決めておくとその日に出る。
  空なら今までどおり「前回＋頻度の日数」。
- 実施記録が店舗ごとなので、**次にやる日も店舗ごと**に持つ
  （`periodicDone_<店舗>` の中の `next`）。店舗によって予定が違うため。
- 完了を押すと、次にやる日は**その日＋頻度の日数**で自動更新される。
- plus α には**それだけのゲージ**がある。上の進捗バー（毎日ぶん）には入れない。
  やると動くので、手ごたえが出る。
- **今日やり終えた分も枠に残す。** 消えると、やったのか分からなくなる。
  タブのバッジ（`periodicDueCount`）は「残り何件か」なので、そちらには足さない。

**項目ごとに頻度を付ける作りは取りやめた**

一度は、チェックリストの項目に `everyDays`（何日に1回）を付けて plus α に
移す作りにした。だが定期清掃と**同じことをする入口が2つ**になり、同じ仕事を
どちらにも登録できてしまう。定期清掃に一本化して、項目側の設定は外した。
（本番に出す前だったので、現場への影響はなし）

**このとき見つけた不具合**

- plus α の定期清掃の行に付けた `onclick` が、あとから走る共通の `.rt-row`
  配線に**上書きされていた**。`.rt-row:not(.plus-periodic)` で外した。
  共通の配線は `row.dataset.id` が無いときに何もしないようにもしてある。
- 補足つきの行で `has-desc` を付け忘れ、折り返さずに**項目名が幅0まで潰れて
  いた**。`.rt-row` は補足があるとき `has-desc` で折り返す作り。

### 2-42. 日付を決めたものだけ plus α に出す

**2-41 を出したら、plus α に定期項目が全部並んでしまった。**

`periodicStatus` は、実施記録が無い項目を「未実施＝実施時期（due）」として
返していた。本番の `periodicDone_<店舗>` には2件しか記録が無く、
**残りは全部「未実施」だった**ので、登録してあるだけの項目が軒並み
「今日やること」として出た。

状態に `unset`（日付未設定）を足して分けた。

| 状態 | いつ | plus α |
|---|---|---|
| `unset` | 一度もやっておらず、やる日も決めていない | **出さない** |
| `due` | やる日が来た／過ぎた | 出す |
| `soon` / `ok` | やる日がまだ先 | 出さない |

`periodicDueCount`（タブのバッジ）と `rvPeriodic`（ふりかえりの期限切れ）も
`due` を見ているので、同じだけ静かになる。日付未設定の項目は定期清掃の一覧に
「日付未設定」として残るので、見失うことはない。

**やる日は一覧から直接decide できる**

編集（ペン）を開かなくても、定期清掃の一覧の各行に日付の入力欄を置いた
（`setPeriodicNext`）。「消す」で日付未設定に戻る。
実施記録とやる日が両方無くなったら、`periodicDone_<店舗>` から鍵ごと消す
（空の殻を残さない）。

**このとき見つけた不具合**

やる日だけ決めた項目は `done` はあるが `date` が無い。一覧の「前回」が
`done` の有無だけを見ていたので、**「前回: undefined（null日前）」**と出ていた。

### 2-43. 繰り返しを「毎週◯曜」「Nヶ月ごと◯日」でも決められるようにする

今までは「何日ごと」だけだった。`task.repeat` を足した。

```js
{ kind: 'days',  n: 30 }              // 30日ごと（今までどおり）
{ kind: 'week',  every: 1, dow: 1 }   // 毎週 月曜（every: 2 で2週ごと）
{ kind: 'month', every: 3, day: 15 }  // 3ヶ月ごと 15日
```

`repeat` が無い項目は `interval`（何日ごと）として読むので、**本番の既存データは
そのまま動く**。保存時は `interval` にもおおよその日数を書いておく
（週＝7×n、月＝30×n）。「そろそろ」の判定と並び順がこれを見ている。

**次の日の出し方**（`nextFromRepeat(task, from)`）

| 決め方 | from | 次 |
|---|---|---|
| 毎週 月曜 | 月曜 9/14 | 9/21（同じ日は返さない） |
| 毎週 月曜 | 火曜 9/15 | 9/21 |
| 毎週 金曜 | 月曜 9/14 | 9/18（今週） |
| 毎月 15日 | 9/20 | 10/15 |
| 毎月 15日 | 9/14（早めにやった） | 10/15 |
| 3ヶ月ごと 15日 | 9/20 | 12/15 |
| 毎月 31日 | 1/15 | 2/28（**末日に丸める**） |

月をまたぐ計算は `new Date(y, m, d)` に任せている（`m` が12を超えても年が繰り上がる）。
末日の丸めは `daysInMonth` で、31日指定でも2月は末日になる。

**ダイアログ**

「繰り返し（どう決めるか）」で ◯日ごと／毎週◯曜日／毎月・Nヶ月ごと◯日 を選ぶと、
下の欄が入れ替わる。選んでいない決め方の欄にも既定値を入れてあるので、
切り替えてすぐ保存できる。

### 2-44. 繰り返しを決めたら、やる日を自動で入れる

2-43 までは、繰り返しを決めても**やる日を手で入れるまで plus α に出なかった**。
決めた時点で入るようにした。

**最初の1回は別の計算**（`firstFromRepeat`）

`nextFromRepeat` は「やり終えた次」を出すので1周期ぶん先になる。
まだ一度もやっていない項目にこれを使うと、毎週月曜なのに来週から、になってしまう。
`firstFromRepeat` は **from 以降で一番近い、その決め方に合う日**（当日を含む）を返す。

| 決め方 | 今日 | 最初の日 |
|---|---|---|
| 毎週 月曜 | 月曜 | **今日** |
| 毎週 水曜 | 月曜 9/14 | 9/16（今週） |
| 毎月 15日 | 9/14 | 9/15（明日） |
| 毎月 10日 | 9/14（過ぎている） | 10/10 |
| 3ヶ月ごと 10日 | 9/14 | 10/10（最初は一番近い10日） |
| ◯日ごと | — | 今日から |

**3店舗ぶんまとめて入れる**（`scheduleFromRepeat`）

決め方は項目に付いていて3店舗で共通なので、店舗を切り替えて入れ直さずに済むよう、
**やる日をまだ持っていない店舗だけ**に入れる。すでに日を決めてある店舗と、
一度やったことがある店舗（前回＋決め方で出せる）は触らない。

**入れ直すのは、繰り返しを決め直したときだけ**

名前だけ直して保存したときに、**消しておいた日が復活しない**ようにするため、
保存前の決め方と見比べて、変わったときだけ入れる（`repeatChanged`）。

また、ダイアログの「次にやる日」を書き込む処理を**自動で入れるより先**に置いた。
順番が逆だと、その欄が空のまま保存したときに、自動で入れたぶんを消してしまう。

### 2-45. 定期清掃の完了を取り消せるようにする

plus α の行はタップすると完了になるだけで、**外す手段が無かった**。
押し間違えると直せない。

- plus α の行は**タップで完了／取消の切り替え**
- 定期清掃の一覧は、今日やった分だけボタンが**「完了」→「取消」**に変わる
- **今日つけた分だけ**取り消せる（`periodicCanUndo`）。
  昨日以前の記録を誤って消さないため

**元の状態を控えてから書き換える**

完了は `date` と `next` を両方書き換えるので、ただ消すだけでは戻らない。
完了時に直前の状態を `prev` に控えて、取消でそこへ戻す。

```
完了前: { next: '2026-09-14' }
完了後: { date: '2026-09-14', staff: '山田', next: '2026-09-21',
          prev: { next: '2026-09-14' } }
取消後: { next: '2026-09-14' }        ← 前の状態に戻る
```

前にやったことがある項目なら、前回の実施日にも戻る。
`prev` は入れ子にしない（控えるときに落としている）。
控えが空（＝もともと何も無かった）なら、鍵ごと消して日付未設定に戻す。

### 2-46. 「やる日」を入れても反映されないことがあったのを直す

`canRefreshNow` は、**`type="date"` の input に触れていても描き直してよい**
ことにしていた（「文字を打たない種類の input は、止める理由にならない」）。
これは日付欄が画面上部の1つだけで、描き直しても作り直されない位置にあったころの話。

2-42 で定期清掃の一覧に「やる日」を置いたが、そこは `renderPeriodic` が
`checklist.innerHTML` ごと作り直す場所だった。そのため、

1. 日付欄をタップしてピッカーが開く
2. その間に他の端末の変更が届く（`refreshAfterPull` → `render`）
3. **入力欄ごと作り直されて、選んでいた内容が消える**

iPad は選び終わるまで数秒かかるので、これに当たりやすい。

`date` を例外から外し、**日付を選んでいる間は描き直しを見送る**ようにした。
見送った分は `focusout` の `flushPendingRefresh` で反映されるので、
選び終われば追いつく。

`activeElement` が当てにならない端末もあるので、`focusin` / `focusout` で
`dateEditing` を自前に持っている。

**画面の中に input を置くときの注意。** `innerHTML` で作り直す場所に置くと、
描き直しのたびに入力が飛ぶ。`canRefreshNow` で止めるか、作り直さない場所に置くこと。

### 2-47. 繰り返しを決めてあるのに、やる日が入らなかったのを直す

現場から動画をもらって分かった。項目には「毎週 月曜」が入っているのに
**「日付未設定」のまま**で、ダイアログを開いて保存し直しても変わらない。

2-44 で入れた `repeatChanged` のせい。**決め方を「変えた」ときだけ**
`scheduleFromRepeat` を呼ぶようにしていたので、すでに同じ決め方が入っている項目を
保存しても何も起きなかった。2-43（決め方を選べるようにした回）と
2-44（自動で入れる回）の間に設定した項目が、全部この状態になる。

**日付を持っていない項目には、決め方を変えていなくても入れる**ようにした。

**「消す」で消したものは復活させない**

条件を外すと、今度は「消す」で消した日が、名前を直して保存しただけで戻ってしまう。
`setPeriodicNext(id, null)` で鍵ごと消していたため、
**まだ決めていないのか、わざと消したのかが区別できなかった**。
消したときに `off: true` の印を残すようにした。

| 店舗の状態 | 保存したとき |
|---|---|
| 何も無い | **入れる** |
| `off`（わざと消した） | 入れない（決め方を変えたときだけ入れ直す） |
| `next` がある | 触らない |
| `date` がある（やったことがある） | 触らない |

### 2-48. チェックを外して付け直したときに、抜き打ち写真の撮り直しを求めない

現場から。写真が要る項目をチェック → **タップミスで外れる** → 付け直すと
また撮影を求められる、という声。

チェックを外すと `delete rec[id]` で記録ごと消えるので、
`proof`（写真へのひも付け）も一緒に消えていた。写真そのものは
`/data/media` に残っているのに、アプリからは「撮っていない」状態に見えていた。

`proofTakenToday(areaKey, itemId)` を足した。写真の鍵が
`proof:<店舗>:<エリア>:<項目>:<日付>:<通し番号>` なので、**そこから直接探せる**
（別の控えを持つ必要がない）。チェックを入れるときに今日のぶんが見つかれば、
撮影を求めずにその写真をひも付ける。

| | |
|---|---|
| 同じ日・同じ項目・同じ店舗 | **撮り直さない** |
| 翌日 / 別の項目 / 別の店舗 | 撮り直す |

エリアは `baseArea` で比べるので、時間帯つきの鍵（`floor@routine_asa`）も拾う。

**担当者は見ない。** 写真は「その日その項目をやった証拠」なので、別の人が
今日撮っていればそれで足りる。付けた人は記録に残る。

**使い回したことは撮影ログに残す**（`reused: true`）。あとから見て
撮り直しでないと分かるようにするため。今日その項目を撮らずにチェックすることは
これまでどおりできないので、抜き打ちの効き目は落ちない。

### 2-49. 笠寺と萩野通の構成を突き合わせた（読み取りのみ・変更なし）

「萩野通のシャワーを笠寺と同じ構成にしたい」という話。本番のデータを読んで
突き合わせた結果、**シャワーの中身はすでに完全に一致していた**。

| | 笠寺 | 萩野通 |
|---|---|---|
| 場所 | `shower_b1`〜`b7`（7ヶ所） | 同じ7ヶ所・**名前も同じ** |
| 各場所の項目 | 14項目 | **同じ14項目・同じ並び・同じ区分** |
| 親の `shower` | 追加4・非表示13・書き換え5 | **まったく同じ** |

違っていたのは次の3点だけ。

1. **やる回数** — 笠寺は朝番の「シャワー清掃」だけ。萩野通は朝番・中番
   「シャワーの見回り清掃」・遅番の3回とも、7ヶ所×14項目のフルセットに繋がっている。
2. **`shower_round`（見回りの場所）** — 萩野通だけにあるエリア。中に場所の名前が
   7つ入っているだけの軽い一覧で、見回り用に作られたように見えるが、
   **どの行からも繋がっていない**（中番の行はフルセットのほうを向いている）。
3. **遅番の「シャワー排水溝ネット交換」「シャワーマット交換」** — 萩野通だけ。

どれを揃えるかで作業が変わるので、ここでは**何も変更していない**。

### 2-50. 萩野通のシャワー清掃を、笠寺と同じく朝番だけにした

上の1（やる回数）を揃えた。本番データのみの変更で、画面ファイルは触っていない。

| | 変更前 | 変更後 |
|---|---|---|
| 朝番「シャワー清掃」 | あり | **あり（そのまま）** |
| 中番「シャワーの見回り清掃」 | あり | **外した** |
| 遅番「シャワー清掃」 | あり | **外した** |

外したのは**連動先にシャワーが入っている行だけ**。遅番の
「シャワー排水溝ネット交換」「シャワーマット交換」は連動先が空なので残っている。
`shower_b1`〜`b7` のエリアと14項目、これまでの記録にも触っていない
（`shower_b1@routine_hiru` のような記録はデータには残る）。

変更後に読み直して、次を確かめた。

- 萩野通のシャワーに繋がる行は朝番の1行だけ
- `shower_b1`〜`b7` が7ヶ所とも残り、どれも14項目
- 遅番の交換2行が残っている
- 笠寺・枇杷島は変わっていない

エリアのタブから直接チェックしたときの入り先（`recArea`）も、連動元が朝番だけに
なったので笠寺と同じく朝番ぶんに入る。

**`shower_round`（見回りの場所）は残したまま**。どの行からも繋がっていないので
画面の動きは変わらないが、中番の見回りを軽くしたくなったらここに繋ぐと使える。


#### 調べ方（ssh が固まる件の回避）

`flyctl ssh sftp get` も `flyctl ssh console` も応答が返らず固まった
（timeout を付けていなかったので10分以上進まなかった）。

- 合言葉は **`flyctl machine exec`（マシンAPI＝HTTP）** で読む。ssh は予備。
- データ本体は **`GET /api/state`**（HTTPS）で取る。`state.media` は種類の文字列だけなので軽い。
- どのコマンドにも `timeout` を付ける。

これで1回20秒ほどで読めるようになった。

登録されているのは**デプロイ用トークン**。できること・できないことは以下のとおり。

- できる：`status` / イメージ取得 / SSH / デプロイ
- できない：ボリュームのスナップショット操作（日次の自動バックアップは別途有効）

## 次に何かする場合の注意

- 項目の削除・変更は `state.json` を直接書き換えず、**アプリのAPI（PUT /api/state/:key）経由**で行うこと。
  サーバーはメモリ上に状態を持っていて、次の保存でファイルを上書きするため。
- 店舗ごとに定義が独立しているので、1店舗だけ変えたい場合は `sdef_<店舗>_...` を対象にする。
- 画面を変えたら `docs/usage-guide.html` とPDFも合わせて更新する。
